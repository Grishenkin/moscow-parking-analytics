
# Бизнес-требования проекта

## Название проекта

**Moscow Parking Analytics — аналитическая платформа парковочной инфраструктуры Москвы**

## 1. Описание проблемы

Информация о парковочной инфраструктуре Москвы публикуется в нескольких отдельных наборах открытых данных.

В рамках проекта используются:

- парковки такси;
- перехватывающие парковки;
- платные парковки.

Наборы имеют разные структуры, названия полей и способы представления географических координат.

Для аналитика неудобно работать с каждым набором отдельно. Требуется единая модель данных и аналитический интерфейс для анализа парковочной инфраструктуры Москвы.

## 2. Цель проекта

Создать data-driven приложение, которое автоматически:

1. загружает данные с API Портала открытых данных Правительства Москвы;
2. обрабатывает и нормализует данные с помощью Apache Spark;
3. объединяет несколько источников в единую модель;
4. выполняет проверки качества данных;
5. формирует аналитические витрины;
6. предоставляет пользователю dashboard для анализа результатов;
7. запускает ETL-процесс автоматически с помощью Apache Airflow.

## 3. Пользователи системы

Потенциальными пользователями являются:

- городской аналитик;
- транспортный аналитик;
- специалист по развитию городской инфраструктуры;
- пользователь, заинтересованный в анализе парковочной инфраструктуры Москвы.

## 4. Основные аналитические вопросы

Система должна позволять отвечать на следующие вопросы:

- Сколько парковочных объектов представлено в данных?
- Каково общее количество парковочных мест?
- Как распределены парковочные объекты по административным округам?
- Какие районы имеют наибольшее количество парковочных объектов?
- Как распределяются разные типы парковок?
- Какова вместимость различных типов парковок?
- Где физически расположены парковочные объекты?
- Какие административные округа и районы обладают большей парковочной инфраструктурой?

## 5. Источники данных

Используются наборы Портала открытых данных Правительства Москвы:

### Dataset 621
Парковки такси.

### Dataset 622
Перехватывающие парковки.

### Dataset 623
Платные парковки.

Данные загружаются через API:

`https://apidata.mos.ru/v1`

Для получения объектов используется GeoJSON endpoint `/features`.

## 6. Функциональные требования

### FR-1. Загрузка данных

Система должна автоматически получать актуальные данные из API для всех трёх наборов.

Загрузка должна поддерживать пагинацию API.

После загрузки количество полученных объектов должно совпадать со значением API `/count`.

### FR-2. RAW-слой

Полученные данные должны сохраняться без бизнес-преобразований в формате GeoJSON.

RAW-данные должны храниться отдельно для каждого источника.

### FR-3. Нормализация данных

Apache Spark должен привести разные источники к единой структуре:

- global_id;
- object_type;
- parking_name;
- adm_area;
- district;
- address;
- longitude;
- latitude;
- capacity;
- schedule;
- source;
- load_date.

### FR-4. Обработка географических данных

Для парковок такси и перехватывающих парковок координаты должны извлекаться из GeoJSON Point.

Для платных парковок геометрия MultiLineString должна преобразовываться в репрезентативную точку для отображения на карте.

### FR-5. Silver-слой

Нормализованные источники должны объединяться Spark в единый набор `parking_objects`.

Результат должен сохраняться в формате Parquet с партиционированием по `object_type`.

### FR-6. Data Quality

Перед формированием аналитических витрин должны выполняться проверки:

- dataset не пустой;
- global_id не NULL;
- object_type не NULL;
- parking_name не NULL;
- adm_area не NULL;
- district не NULL;
- longitude не NULL;
- latitude не NULL;
- capacity не NULL;
- capacity > 0;
- координаты находятся в допустимых диапазонах;
- отсутствуют дубли по global_id + object_type;
- присутствуют ожидаемые типы парковочных объектов.

Поля `address` и `schedule` могут содержать NULL, если значение отсутствует в исходном наборе данных.

### FR-7. Gold-слой

Spark должен сформировать аналитические витрины:

#### district_summary

Агрегаты по районам:

- количество парковочных объектов;
- количество парковок такси;
- количество перехватывающих парковок;
- количество платных парковок;
- общая вместимость;
- средняя вместимость.

#### adm_area_summary

Агрегаты по административным округам.

#### object_type_summary

Статистика по типам парковочных объектов:

- количество объектов;
- общая вместимость;
- средняя вместимость;
- минимальная вместимость;
- максимальная вместимость.

#### parking_map

Набор координат и характеристик объектов для отображения на карте.

### FR-8. Dashboard

Пользователь должен иметь возможность:

- увидеть основные KPI;
- сравнивать административные округа;
- анализировать районы;
- видеть структуру парковочной инфраструктуры;
- фильтровать данные;
- отображать парковочные объекты на карте Москвы.

Dashboard реализуется с использованием Streamlit и Plotly.

### FR-9. Оркестрация

Apache Airflow должен запускать задачи в последовательности:

download_sources
→ normalize_parking
→ build_unified_dataset
→ build_marts
→ quality_checks

Pipeline должен автоматически запускаться каждый понедельник в 06:00 по московскому времени.

При ошибке задача должна иметь две повторные попытки с интервалом 5 минут.

Одновременно допускается не более одного активного запуска pipeline.

## 7. Нефункциональные требования

Система должна:

- использовать Apache Spark как основной инструмент обработки данных;
- хранить обработанные данные в Parquet;
- не хранить API-ключ в Git;
- иметь воспроизводимые Python-зависимости;
- иметь отдельное окружение для Spark-приложения и Airflow;
- содержать автоматические тесты;
- быть представлена в GitHub-репозитории;
- иметь документацию по запуску.

## 8. Текущий результат

На используемой версии данных:

- 16 127 парковочных объектов;
- 180 284 парковочных места;
- 15 638 платных парковок;
- 356 парковок такси;
- 133 перехватывающие парковки;
- 124 района;
- 11 административных округов.

Все Data Quality проверки проходят успешно.
